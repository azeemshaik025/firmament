### Reference implementation

`src/application/runtime/reconciliation/mod.rs::run_loop` is the canonical pattern. Pattern summary:

```rust
pub async fn run_loop(
    orchestrator: Arc<RuntimeOrchestrator>,
    config: AutomationConfig,
    shutdown: Arc<tokio::sync::Notify>,
) {
    let mut interval = tokio::time::interval(Duration::from_secs(config.rebalance_interval_seconds));
    interval.set_missed_tick_behavior(tokio::time::MissedTickBehavior::Skip);
    loop {
        tokio::select! {
            _ = interval.tick() => {
                if let Err(error) = run_one_rebalance_tick(&orchestrator).await {
                    tracing::warn!(?error, "rebalance worker tick failed");
                }
            }
            _ = shutdown.notified() => break,
        }
    }
}
```

### Decision logic and where it lives

`src/application/rebalance.rs` already has:
- `decide_rebalance(snapshot, policy, registry, ...) -> Option<RebalancePlan>` — bidirectional weight rebalance
- `decide_gateway_refill(snapshot, ...) -> Option<RefillPlan>` — checks `usdc_refill_threshold_raw`
- `maybe_native_sol_top_up(...) -> Option<TopUpPlan>` — Jupiter swap to keep gas funded

Execution is wired through `submit_planned_swap` and `gateway_client.request_refill`. The orchestrator path is at `src/application/runtime/orchestrator.rs:1725-1825` (`run_automation`).

**Splitting strategy** (recommended): factor `run_automation` into three scoped methods on `RuntimeOrchestrator`:

```rust
pub async fn run_rebalance_check(&self) -> AppResult<AutomationOutcome> { ... }
pub async fn run_gateway_refill_check(&self) -> AppResult<AutomationOutcome> { ... }
pub async fn run_native_top_up_check(&self) -> AppResult<AutomationOutcome> { ... }
```

Each loop calls one method only — keeps the loops cleanly orthogonal and avoids three loops all running the full `refresh_inventory_and_automation`.

### Race protection

`accept_quote` calls `refresh_inventory_and_automation` (`orchestrator.rs:952`) inside the trade flow. If a worker tick fires concurrently, two simultaneous Jupiter swaps could land. Add a `Mutex<()>` on the orchestrator:

```rust
automation_lock: Arc<tokio::sync::Mutex<()>>,
```

Held for the duration of any automation execution (both the trade-driven path and the worker-driven path). This serializes them. Tokio's async mutex is fine — these are short-held.

## Gap 2 — Excess working_custody → Gateway deposit

### What this flow does

When `working_custody:USDC` exceeds a configurable threshold, deposit the excess INTO Circle Gateway. This is the **opposite direction** of the existing Gateway refill (which pulls Gateway → working_custody). Munger doesn't have this for Solana, so this is going beyond Munger's reference.

Ledger movement:
1. **Submit** (deposit instruction sent to Solana): `working_custody → pending_gateway_deposit`
2. **Confirm** (deposit appears in Circle Gateway provider balance): `pending_gateway_deposit → gateway`

### Lifecycle wiring

In `src/adapters/persistence/ledger.rs::transactions_for_event`, add arms:

```rust
RuntimeEvent::Gateway(GatewayEvent::DepositSubmitted { amount, .. }) => {
    let asset = amount.asset.clone();
    let amount_raw = amount.amount_raw;
    let txn = LedgerTransactionBuilder::new("excess_deposit", uuid::Uuid::now_v7())
        .description(format!("excess working_custody {asset} -> pending_gateway_deposit"))
        .idempotency_key(format!("excess-deposit:submit:{asset}:{utc_seconds}"))  // dedupe by-second
        .debit(LedgerAccountId::pending_gateway_deposit(asset.clone()), amount_raw)
        .credit(LedgerAccountId::working(asset), amount_raw)
        .build_at(metadata.occurred_at)?;
    transactions.push(txn);
}

RuntimeEvent::Gateway(GatewayEvent::DepositConfirmed { amount, .. }) => {
    // pending_gateway_deposit -> gateway
}
```

Choose the idempotency-key scheme deliberately — there's no `trade_id` to anchor on. A timestamp-bucketed key (e.g. `excess-deposit:submit:USDC:{utc_iso}`) keeps the lookup deterministic but allows reruns within the same second to dedupe; alternative is a per-deposit uuid persisted on the event metadata. Document the choice.

### Decision logic shape

```rust
// src/application/rebalance.rs

pub fn decide_excess_deposit(
    snapshot: &ValuedInventorySnapshot,
    config: &GatewayConfig,
) -> Option<ExcessDepositPlan> {
    let working_usdc = snapshot.working_custody_raw("USDC")?;
    if working_usdc <= config.usdc_excess_deposit_threshold_raw {
        return None;
    }
    let excess = working_usdc.saturating_sub(config.usdc_excess_deposit_target_raw);
    if excess == 0 { return None; }
    Some(ExcessDepositPlan { amount_raw: excess })
}
```

## Gap 4 — Native SOL top-up chains Gateway refill

### What this flow does

Munger's flow when SOL gas runs low:
1. Check working USDC.
2. If working USDC is below the amount needed for the SOL purchase swap, **call Gateway refill first** to pull USDC from Gateway → working.
3. Then Jupiter-swap USDC → SOL.

Firmament's `maybe_native_sol_top_up` only does step 3 — if working USDC is short, the swap fails or undersizes.

### File map

| File | Change |
|---|---|
| `src/application/rebalance.rs` `maybe_native_sol_top_up` | rewrite to be aware of Gateway as a USDC source |
| `src/application/runtime/orchestrator.rs::run_native_top_up_check` (new from Gap 3) | sequence: call `gateway_client.request_refill` if needed, then `swap_executor.execute_swap` |

### Implementation sketch

```rust
async fn run_native_top_up_check(&self) -> AppResult<AutomationOutcome> {
    let snapshot = self.inventory_snapshot().await?;
    let plan = match maybe_native_sol_top_up(&snapshot, &self.config) {
        Some(plan) => plan,
        None => return Ok(AutomationOutcome::NoActionNeeded),
    };

    let working_usdc = snapshot.working_custody_raw("USDC").unwrap_or_default();
    if working_usdc < plan.usdc_input_raw {
        // Need a Gateway refill first.
        let shortfall = plan.usdc_input_raw - working_usdc;
        let refill_amount = shortfall + self.config.gateway.usdc_refill_buffer_raw;
        let receipt = self.adapters.gateway_client
            .request_refill(GatewayRefillRequest { amount_raw: refill_amount })
            .await?;
        // emit Gateway::RefillCompleted etc.
    }

    // Now run the swap.
    let receipt = self.adapters.swap_executor.execute_swap(/* ... */).await?;
    // emit Swap::Executed
    Ok(AutomationOutcome::Submitted { summary: format!("native_top_up via gateway: {refill_amount} USDC") })
}
```

## Architectural risks Codex should know about

### Same-domain Gateway adapter only returns one signature

The Solana same-domain Circle Gateway adapter atomically does burn+mint and returns a single on-chain signature (the `gatewayMint`). Gap 1 surfaces that signature on both `BurnIntentSubmitted` and `MintConfirmed`. Don't try to thread two distinct signatures through — there isn't one to find. If a future cross-chain Gateway adapter splits these, the event variants already accept distinct values.

### Race between trade-driven and worker-driven automation

After Gap 3's mutex lands, this becomes deterministic. Before Gap 3, calling the admin endpoint while a trade is settling can double-fire automation. Don't wire the excess-deposit endpoint until the mutex is in place.

### Idempotency keys for non-trade-scoped operations

Trade lifecycle uses `ledger:trade:{trade_id}:{transition}`. Reconciliation uses `recon:{scope}:{asset}:{utc_date}:{seq}`. Cold-start seed uses `bootstrap-seed:working_custody:{asset}` (one-shot, idempotent on restart). Excess deposit needs its own scheme — recommend `excess-deposit:{phase}:{asset}:{minute_bucket}` so within-minute reruns dedupe but you don't lose history. Document whichever scheme you pick.

### LedgerEventConsumer is constructed per-event

Phase 1 found this. State is in the database, not in memory on the consumer. Don't try to add stateful logic to the consumer; persist any state via ledger entries with idempotency keys.

### Config validation

`AppConfig::load()` validates per-asset notional (Phase 4 just added). Excess-deposit thresholds need a sanity check too: target ≤ threshold and both ≥ 0. Add validation in `GatewayConfig::validate`.
